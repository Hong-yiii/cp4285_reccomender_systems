03 / OBJECTIVE AND METHOD

Keep the measuring stick fixed while the model changes.

Retention means maintaining quality on the original task after further training. Adaptation means learning the new task. A frozen model can retain perfectly by refusing to learn anything; that is why a future B experiment also needs a B metric.

The solution method is controlled branching: select one A checkpoint, make independent copies for each condition, then keep A histories, targets, candidate items and ranking rules identical across checkpoints. The incoming training stream changes; the test does not.

Loss of initial capability

Retention loss =
A score at start − A score now

Positive means worse than the initial model. Negative means improvement.

Effect versus continued A training

Mixture effect =
mixed A score − A-only A score

Negative means worse than A-only at the same update budget. That is not automatically forgetting relative to the start.

INFERENCE A model can improve over its initial score yet improve less than A-only. Calling both comparisons “forgetting” would hide what you actually measured. Improvement or no detectable change is an acceptable outcome; do not choose data to force a decline.

docs/CONTINUED-TRAINING.md, “Evaluation and comparison,” defines the two signed quantities and the fixed-A contract; docs/EXPERIMENT.md, “Comparison conditions,” explains the reduced-A-exposure confound.

04 / END TO END

Follow one event from a CSV to a retention score.

1. Ingest observations, not assumed preferences.

The official ID-only input is user_id,parent_asin,rating,timestamp. The default task uses all ratings to predict the next reviewed item. A one-star review is still a review event, not an endorsement. Review time is not necessarily purchase or viewing time.

The audit checks schema, ratings and Unix milliseconds; counts exact duplicate rows, repeated user-item pairs, ambiguous same-user timestamp ties and original-ID overlap. It estimates usable history lengths. Reindexed “user 17” in two files does not prove the same person; overlap must use original IDs.

src/cp4285/data.py:64–87 validates input values; src/cp4285/data.py:98–172 builds the audit. The official 5-core documentation confirms the ID-file schema and lists approximately 15.5M Electronics and 7.4M Movies & TV ratings—publisher statistics, not your audit results.

2. Construct a familiar-item, fixed-A task.

Preparation removes exact duplicates and all ambiguous tied events. It selects at most 500 reviewers using initial-period eligibility and a seeded hash, not whether they happen to return later. For each user, the last two events before the cutoff are held out. The earlier prefix supplies initial training and the item vocabulary—the list of item IDs the model knows.

Unknown held-out or later items are omitted and counted. Unknown later items also stay out of histories. This makes the first pilot a familiar-item experiment, not a new-item cold-start study. The same product may legitimately appear in another event; isolation is about held-out events, not banning that product ID from the whole dataset.

src/cp4285/data.py:189–208 selects users and reserves events; src/cp4285/data.py:230–243 builds the shared-prefix holdouts and later stream; src/cp4285/data.py:249–263 records omissions and the global-5-core caveat.

3. SASRec turns a history into item scores.

SASRec is a self-attentive sequential recommender: learned item vectors and position vectors represent the history; causal attention allows each position to use earlier positions but not future ones. The final position represents the user's current sequence. Its dot product with each candidate item's vector produces a ranking score. There is no separately learned user-ID embedding in this implementation.

The original architecture is not just a generic Transformer with the SASRec name. This port preserves normalized queries with raw keys/values, normalized-input residuals, no attention output projection, hidden→hidden→hidden feedforward layers, and layer normalization epsilon 1e-8.

src/cp4285/model.py:20–53 implements the original block; src/cp4285/model.py:81–98 enforces fixed left-padding and scores using the final representation. docs/SASREC.md:7–34 pins source commit e3738967fddab206d6eeb4fda433e7a7034dd8b1 and documents the fidelity checklist.

What “original SASRec” does—and does not—mean here

Preserved: the original architecture, tied item scoring, sampled binary next-item objective, upstream-style user sampling, Adam betas (0.9, 0.98) and the default architecture size.

Different: PyTorch/Python 3.12 rather than Python 2/TensorFlow 1.12; different random initialization draws and optimizer arithmetic; stable softplus loss rather than epsilon-clipped logarithms; this project's temporal split, full-catalogue evaluator, validation selection and continuation policy.

Not claimed: a TensorFlow execution, bitwise cross-framework parity, conversion of TF checkpoints, or reproduction of the paper's benchmark numbers. The NumPy reference test is useful equation evidence, not a live TensorFlow comparison. Earlier generic SequentialRecommender checkpoints are incompatible.

docs/SASREC.md:36–64 makes these boundaries explicit. The inspected upstream modules.py supplies the attention/residual equations; sampler.py supplies sequence construction.

4. Initial training and continuation intentionally supervise different positions.

Given history [0, 0, 1, 2, 3], new target 4 Supervised targets Reason
Initial training [0, 0, 2, 3, 4] Train all valid next-item positions in a sampled user's final window.
Continuation [0, 0, 0, 0, 4] Use old positions as context; learn only from the fresh target.

Each active position gets one negative—an unobserved alternative, not a confirmed dislike. Initial negatives exclude that user's entire initial item set; continuation negatives exclude the supplied history and fresh target. The loss raises observed-item scores and lowers sampled-alternative scores.

INFERENCE Reusing all-position supervision during continuation would silently re-train on old targets. That is historical replay, not the promised fresh-target-only condition.

src/cp4285/pilot.py:31–61 builds the initial user sequences and target masks; src/cp4285/model.py:100–114 averages the sampled loss over active targets; tests/test_sasrec.py:92–109 verifies the distinction.

5. Select once, reload, then continue without resetting the model.

Initial epochs are evaluated on validation NDCG. The best validation checkpoint is saved, evaluated on retention, reloaded and checked for matching scores. One copy stays frozen. Another consumes chronological A batches, preserving model weights and Adam's running optimization statistics across cycles. Adam resets once at the initial-to-continuation boundary, not every cycle.

A cycle is a configured block of optimizer updates, not a day of real time. Each cycle saves model, optimizer, stream position and recorded RNG state. Saving state is not the same as having a resume command: interruption/restart is not wired into the CLI yet.

src/cp4285/pilot.py:158–196 selects and verifies the checkpoint; src/cp4285/pilot.py:197–232 performs fresh updates, frozen checks and saves; docs/IMPLEMENTATION.md:85 explicitly limits restart support.

6. Rank against the same original catalogue.

At each checkpoint, the evaluator scores the same A prefixes and targets against every nonpadding item in the initial training catalogue. It does not remove previously seen items, because repeated review events are allowed. Exact score ties use the lower item index consistently.

Recall@10 is the proportion of targets that reach the top 10 here; with one target per example, this is also Hit@10. NDCG@10 rewards a higher rank: a single target at rank 1 scores 1, rank 3 scores 0.5, and rank 11 scores 0. Average over retained examples.

INFERENCE These scores measure retention on a fixed historical anchor—not accuracy on an evolving population of future users. Adding B candidates to A evaluation would change the measuring stick and constitute a different experiment.

src/cp4285/pilot.py:64–100 defines deterministic ranking and averaging; src/cp4285/model.py:97–98 constructs the full score matrix.

06 / PROPOSED EXTENSION — NOT IMPLEMENTED

For B to affect A, you need a real path through shared parameters.

The proposed neural design has separate A/B item interfaces and a shared SASRec sequence encoder. The encoder is the learned function that transforms a history into a vector. B can change this shared function even when A and B have no common people or products.

Do not concatenate unrelated users' histories or make unrelated local item IDs coincide. An A example must still represent a real A history. Adding a freshly initialized B interface should leave A's initial scores unchanged; this needs a regression check before comparing branches.

For matrix factorisation, a classical model that scores a user-item pair with learned user and item vectors, the influence path can differ. If A and B factors are disjoint and B updates truly leave every A-scoring parameter untouched, A scores cannot change. That flat curve is an isolation control, not proof that classical models generally resist forgetting. Genuine shared users, shared parameters, decay or optimizer behavior can change the conclusion.

docs/CONTINUED-TRAINING.md, “Model and training examples” and “Stage 1,” specifies the proposed interfaces and unchanged-A requirement. docs/DATASET-ASSESSMENT.md, “Mechanism and group-comparison implications,” explains the separate classical sharing audit.

Mixing ratios need a denominator and an exposure control.

α = B supervised targets / all continued-training supervised targets
If a draft instead says B/A = 200%, then α = 2 / (1 + 2) = ⅔, not 200%.
Illustrative condition A targets B targets Total targets
A-only, α = 0 1,920 0 1,920
Mixed, α = 0.5 960 960 1,920
B-only, α = 1 0 1,920 1,920

Arithmetic illustration using the current continuation budget: 128 × 5 updates × 3 cycles. Only A-only currently runs; these are not executed mixture results or a validated budget.

INFERENCE More B under fixed total updates also means less A practice. A mixed-versus-A-only gap measures stream composition, not harmful B gradients alone. An extra control can use the mixed run's exact A examples while skipping B updates; that matches A exposure but not compute, so optimizer/scheduler timing must be documented.

RECOMMENDATION Before implementing mixtures, agree how to count targets, preserve per-domain chronological order, initialize B identically across branches, handle inactive-domain optimizer parameters, evaluate B learning and repeat across seeds. Average a correctly sampled mixture once; do not apply the mixture coefficient again to each example's loss.

Other assumptions and boring failure modes worth remembering
  • Five-core is not five usable pre-cutoff events. The provided population was filtered using full-history activity. Disclose that selection limitation; a strict temporal-population study would need training-period eligibility from less globally filtered inputs.
  • The audit is not the prepared population. Its later-activity count does not apply the full configured end window and familiar-item/cohort constraints. The default pilot requires at least 1,920 fresh continuation examples; the gate uses the actual prepared stream, not raw counts.
  • Empty splits stop execution. Too strict a rating threshold, too much OOV loss or sparse histories can leave no validation/retention/continuation data. Inspect counts rather than silently recycling examples.
  • Negatives can run out. If a history's exclusion set fills the catalogue, training raises an error. Near-exhausted catalogues make rejection sampling inefficient. Adjust the legitimate cohort/catalogue, not held-out labels.
  • Run protection is not restart support. After interruption, an existing run directory is refused. Do not delete checkpoints to force a rerun; use a new output directory. Implement resume only if longer runs need it.
  • DuckDB spill is relative to the working directory. src/cp4285/data.py:90–95 sets data/.duckdb-spill, while config inputs are rooted to the repository. Run from the documented root; root the spill path before promising arbitrary-directory use. The 2GB DuckDB limit is not a cap on all Python/Torch memory.
  • B-only optimization must really leave A-only parameters inactive. A zero-valued loss is not always enough when optimizer momentum or decay exists. Test unchanged A item parameters and changed shared/B parameters under the agreed policy.
  • Offline logs omit feedback loops. They cannot establish how recommendations would change what people encounter or review. Error analysis should include sparse versus frequent users/items; category B is not inherently malicious “contamination.”

Protect the evidence before spending compute.

Objective: a damaged download must not look complete, and a repeat command must not silently replace the report or split behind an existing result. These are software-integrity requirements, separate from whether the research design is valid.

The old header-only promotion was bad design because readable first bytes do not prove a complete gzip. Directly rewriting prepared JSON was bad design because it could erase the exact experimental input while leaving old model results behind. The smallest shared fix is stricter publication at those two boundaries, not a new experiment framework.

The JSON path uses the existing save_json helper: serialize a complete document and reject nonfinite values such as NaN, write it to a temporary file in the destination directory, then use os.link. A hardlink gives the completed file another filesystem name; creating that name fails if a file or symlink already occupies it. That final check also protects against another writer arriving after the preliminary existence check.

The same helper now protects audit reports, prepared snapshots, download manifests, neural metrics and classical JSON reports. Failed ordinary attempts clean up their own temporary files. No overwrite flag, new dependency, dataset download or model/protocol change was added.

Assumptions, tradeoffs and recovery limits
  • Hardlink support is required. Unsupported filesystems fail rather than fall back to an unsafe overwrite.
  • Atomic visibility is not power-loss durability. A complete final filename becomes visible at once; this is not a claim that all bytes survive an abrupt machine failure.
  • Data and manifest are separate publications. If the manifest write fails afterward, validated raw data is deliberately retained. Inspect the situation; do not delete it blindly to force a retry.
  • Process termination can leave temporary files. Normal error paths clean up; a killed process may leave an unpromoted file. A new attempt uses a new temporary filename.
  • Integrity is not authenticity or semantic validity. Gzip checks detect damaged compressed content. The recorded SHA-256 is provenance, not a publisher-authenticated checksum; row/value checks still belong to the audit.
  • New output paths remain necessary. Repeat audits use a new --output; a new prepared split needs a new data.prepared config path. Existing model run directories remain protected. Cache and checkpoint-resume behavior is unchanged.

17 / SASREC, FROM EVENTS TO SCORES — 28 SEPTEMBER 2026

What goes into SASRec, what it learns, and what retention measures.

SASRec means self-attentive sequential recommendation. It turns a sequence of item IDs into context-dependent vectors. We use those vectors to learn from observed next items, then rank a fixed held-out item after learning continues. The model architecture and our experimental timeline are two different parts of that story.

Scope: this explains the implemented original-architecture PyTorch port and our current A-only pilot, not a new model or an Amazon result. The small numbers below are invented for tracing tensors. The earlier walkthrough remains intact; this appendix sharpens its terminology and adds detail.

Events and vocabulary · One reviewer · Tensor shapes · Inside attention · Training objective · Retention arithmetic · What changes · Runnable check and sources

1. The model sees item IDs—not stars, ASIN strings or user embeddings.

A source row is (user_id, parent_asin, rating, timestamp). Preparation filters ratings, removes exact duplicate rows and ambiguous same-user timestamp ties, chooses the bounded cohort from initial-period eligibility, and orders the remaining events. The default min_rating = 1.0 keeps every valid 1–5-star review as an event. A one-star review is still an observed next item, not a positive endorsement.

User identity groups the sequence; timestamps determine ordering, the cutoff and the continuation window. Neither becomes a model feature. Ratings do not enter the tensor or serve as regression labels. Learned sequence positions encode slot order, not elapsed days. There is no learned user-ID table in this SASRec implementation. 

Raw, chronologically ordered reviews:
(user, product A, 5 stars, t1)
(user, product B, 1 star,  t2)
(user, product C, 3 stars, t3)

After mapping these products to illustrative IDs:
history = [1, 2]    target = 4
Question: which item comes next? Not: how many stars will item 4 receive?

The catalogue is the sorted union of products in the selected users' initial training prefixes, excluding their final two pre-cutoff events as vocabulary-building observations. If item_ids[i] is an original ASIN, its model ID is i + 1. With N = len(item_ids), IDs run from 1 to N; ID 0 is padding only.

The item table stays the same size

E.shape = [N + 1, d]. Every real catalogue row is allocated immediately and initialized with random Glorot/Xavier values. Row 0 is set to zero and stays zero under the normal training path. There are no null rows reserved for future products.

The permitted history can grow

A later review of a known item can extend that user's prefix. An unseen ASIN has no ID or embedding here: its event is counted as out of vocabulary (OOV), skipped, and never appended. New products require a different, explicitly designed catalogue-expansion experiment.

Allocated does not mean well trained. A product's initial review qualifies it for the catalogue, but final-window truncation and stochastic user sampling can leave a row without an update in the short pilot. With default embedding L2 of zero, merely having a row does not guarantee a useful learned representation or even initial gradient exposure.

Sources: data.prepare, SASRec.__init__, pilot defaults.

Each actual record also keeps user and timestamp; the model-facing fields are a one-dimensional history list and one integer target. Preparation clips each stored history to its last L IDs and sorts examples by timestamp then user. It constructs these rows before training: SASRec does not append its predictions to the observed history in this pilot.

If 7 or 8 were OOV, that corresponding validation or retention example would be omitted and counted; one split can keep a user whom the other drops. Other examples for that user need not disappear. An entirely empty partition stops preparation rather than producing a meaningful zero score.

Hold out events, not product IDs. The reserved review events do not become training targets or training history entries. Their products are not globally forbidden: a retained target must already be familiar from some initial training observation, possibly an earlier review by this same user. A different, later review of that same product can also be a legitimate continuation event. Equal item IDs do not identify equal review events.

Both validation and retention ask from the training prefix ending at 4. Retention is therefore a fixed historical-anchor task that skips the validation event, not the usual immediate-next-item test from a prefix including 7. This is our current experiment contract, not a requirement of SASRec. Its interpretation and potentially different retained cohorts remain research-design questions.

3. From integers to contextual vectors to catalogue scores.

Let b be batch size (not domain B), L history width, d hidden size, and N catalogue size. Defaults: L = 50, d = 50, two blocks, one attention head and dropout 0.5. L and d happen to share a value; sequence length and vector width are different axes and can be configured separately.

ObjectShapeMeaning
History tensor[b, L], integerIDs, not one-hot vectors or ratings.
Item table E[N + 1, d]Shared by every user and by input lookup/output scoring.
Position table P[L, d]Learned vectors for slots 0 through L − 1.
Forward states[b, L, d]One context-dependent vector per input position.

X = Dropout(sqrt(d) * E[history] + P[0:L])
X = X * history_nonpadding_mask
H = FinalLayerNorm(two_SASRec_blocks(X))
scores = H[:, -1, :] @ E[1:].T

The input item vectors are scaled by √d; position vectors are not. Positions are learned absolute sequence slots, not sinusoidal features. Fixed left-padding keeps the latest item at index 49 for L = 50 regardless of other examples in the batch. Empty histories and internal padding gaps are rejected by the model.

forward returns states, scores returns raw real-valued scores, and sampled_loss returns a scalar objective. None returns predicted stars. Sorting scores would give a recommendation order, but the evaluator only counts which items outrank the target. A high score is not a calibrated next-item probability; the scoring API applies no catalogue-wide softmax.

Sources: tensors; SASRec.forward and scores.

4. Inside a block: attention mixes the prefix; feedforward transforms each position.

A query represents what one position is looking for; keys represent what the available positions offer; values carry the information to combine. These are learned linear projections, not separate raw input fields. Similar query/key vectors receive larger attention weights, which mix the corresponding value vectors.

Attention may look at the current input item and earlier permitted items, never a later input position. In the toy initial history, the state at item 1 predicts 2 without attending to the later input 2; the state at 2 predicts 3 without attending to input 3. This causal mask lets several next-item losses be computed in parallel without giving an earlier prediction its future input. 

Real query position     May attend to      Supervised next item
item 1                 1                  2
item 2                 1, 2               3
item 3                 1, 2, 3            4

Item 4 is a label in this initial window, not an input to it.
The exact block equations and masks used by this port

For H attention heads, each head has width d_h = d / H; d must be divisible by H. Q, K and V become [b, H, L, d_h], and attention logits have shape [b, H, L, L]. The default H = 1 uses all 50 features in one head. Each Linear below includes a learned bias. 

U = LN_attention(X)                    # normalize each d-feature vector
Q = Linear_Q(U)
K = Linear_K(X)
V = Linear_V(X)

A = softmax(mask(Q @ K.transpose(-2, -1) / sqrt(d_h)))
A = A * query_present_mask
Y = concat_heads(Dropout(A) @ V) + U   # no attention output projection

Z = LN_feedforward(Y)
F = Dropout(Linear_2(Dropout(ReLU(Linear_1(Z)))))
X_next = (Z + F) * history_nonpadding_mask
  • Normalization: layer norms have learned scale/bias and epsilon 1e-8; they normalize features within a position, not across users.
  • Key mask: upstream-style presence is computed from nonzero incoming sequence vectors. It is combined with a lower-triangular causal mask.
  • Query mask: presence is computed from normalized queries. The original history-ID mask is reapplied after every block so padded computations do not become context for the next block.
  • All-masked rows: masked logits use finite −(2**32) + 1, avoiding all-negative-infinity softmax NaNs. Padded results are subsequently discarded by remasking.
  • Feedforward: two pointwise d→d linear layers with ReLU between them, equivalent to width-1 convolutions. Attention mixes positions; these layers transform each position's features separately.
  • Residuals: attention adds U, not raw X; feedforward adds Z, not its unnormalized input. Concatenated heads have no extra output projection.
  • Dropout: used on input embeddings, attention weights and both feedforward stages during training; disabled by model.eval(). Attention softmax is over history positions, not catalogue items.

A final layer norm follows the blocks. Its learned bias means final padded output vectors need not be identically zero; this is harmless here because padded targets are excluded and scoring uses the nonpadding last position. The item-table padding row itself remains zero.

Sources: SASRecBlock.forward, reference_states and equation tests, pinned upstream fidelity checklist. NumPy equation checks are not execution of the original TensorFlow runtime or reproduction of its benchmarks.

5. Training scores two items per active position—not the whole catalogue.

At a supervised position the contextual vector is h ∈ R^d. The positive is an observed next item; the negative is one randomly sampled eligible item, not a known dislike. Both scores use the same item table E that supplied the input embeddings, with no separate output table.

s+ = h · E[positive]
s− = h · E[negative]
ℓ = softplus(−s+) + softplus(s−)
= −log σ(s+) − log σ(−s−)

Here σ is sigmoid, and softplus(x) = log(1 + exp(x)), evaluated with PyTorch's numerically stable implementation. Averaging this sum over M active positions yields one loss; it is not divided by all padded slots or by 2M. At both scores zero, a position contributes 2 log 2 ≈ 1.3863.

This is two independent binary logistic terms, not a BPR objective on s+ − s−, a margin constraint, or full-catalogue cross-entropy. Its direct score gradients encourage s+ upward and s− downward; finite shared-parameter updates do not guarantee the positive outranks every alternative, or that retention improves after each step. 

loss = mean_over_active_positions(softplus(-s_positive) + softplus(s_negative))
     + 0.5 * l2_emb * (sum(E**2) + sum(P**2))

The optional L2 term penalizes item and position embeddings only. With l2_emb = 0.0 it contributes zero. It is not blanket weight decay over the encoder. Dropout is still active during training.

Initial phase: one final window per sampled user, with shifted labels

The three stored training rows above are not trained as three overlapping windows. initial_sequences chooses the final row for this user and reconstructs their entire initial seen-item set from all stored rows. Users are sampled uniformly with replacement; their final windows provide all-position supervision. Earlier items beyond the window are not repeatedly supervised merely because the prepared JSON contains earlier rows. 

# Toy L = 5. Each line has exactly five positions.
history   [0, 0,  1,  2,  3]
positive  [0, 0,  2,  3,  4]
negative  [0, 0, n1, n2, n3]
active    [0, 0,  1,  1,  1]

Each n is a separate uniform draw from 1…N rejecting this user's entire initial training item set, here {1,2,3,4}, even when some of those items lie outside the final visible window. Draws can repeat. Sampling never consults held-out labels to exclude their IDs: an otherwise eligible validation/retention product can be sampled as a negative. If no eligible negative exists, the code raises an error rather than looping forever.

Continuation: only the fresh final target has a loss

# First later known event: item 5
history   [0, 1, 2, 3, 4]
positive  [0, 0, 0, 0, 5]
negative  [0, 0, 0, 0, n]

history   [1, 2, 3, 4, 5]

Continued negatives reject the supplied history and fresh target, not the entire historical user set or future observations. Here the exclusions are {1,2,3,4,5}, then {1,2,3,4,5,6}. After a history is truncated, older omitted IDs are not automatically excluded. Positive zero marks an inactive loss slot; it is not training against padding as a real product.

Context is not frozen just because its label is masked. Earlier positions have no separate replayed target losses during continuation, but the fresh-target gradient still flows through attention and the embeddings of historical context items. The input/output table is tied. Thus “old items are not trained again” is too strong; “old target losses are not replayed” is the intended guarantee. A real repeated review can also be a fresh event.

Sources: initial_sequences, training_tensors and update; sampled_loss.

6. Retention is a ranking metric, not the training loss.

Validation uses [0,1,2,3,4] → 7; retention uses [0,1,2,3,4] → 8. Evaluation switches off dropout and gradients, scores every real item in the initial catalogue, and does not exclude seen products. The target score is column 8 − 1, because score column zero corresponds to item ID 1 rather than padding.

“Training never uses full ranking” needs qualification: the gradient loss uses sampled items, but full-catalogue validation runs after each initial epoch and selects the checkpoint. The first best validation NDCG checkpoint is kept; ties do not replace it. Retention is never used to select that checkpoint.

rank(r) = 1 + count(sj > sr)
  + count(sj = sr and j < r)
Recall@10 = 1 if rank ≤ 10, otherwise 0
NDCG@10 = 1 / log₂(rank + 1) if rank ≤ 10, otherwise 0

These are per-example quantities with one relevant target. Recall@10 is therefore also Hit@10. Reported metrics are their mean over the retained evaluation examples, not over all originally selected users. OOV omissions can change that denominator before training; it stays fixed across continuation checkpoints.

7. What changes when the stream continues?

Adam can update the item table, positional table, attention projections, feedforward layers and normalization parameters through the fresh loss; no layer is deliberately frozen in the A-only continuation branch. Sparse example exposure does not imply every row changes on every step. Model weights carry forward; Adam is reset once at the phase boundary and retained across later cycles. Default learning rates are 0.001 initially and 0.0001 for continuation.

Prefix growth belongs to data construction: after observing known item 6, the permitted full prefix is [1,2,3,4,5,6]; the next L=5 window would be [2,3,4,5,6]. The retention row still uses [0,1,2,3,4] and target 8. Conceptually its cohort has an [R,L] history matrix for R retained examples, but evaluate actually builds and scores it batch by batch each time.

The pipeline saves the validation-selected initial checkpoint, verifies reload scores and evaluates two branches: an unchanged frozen copy and fresh A-only continuation. Default cycles consume 128 × 5 × 3 = 1,920 fresh targets, without silently recycling an exhausted stream. Default three initial epochs give just nine updates at 500 initial users—not evidence of convergence or thorough catalogue coverage.

B-domain interfaces, mixed neural updates and a common-protocol classical/neural comparison remain unimplemented. This architecture explanation neither resolves the fixed-anchor split question nor demonstrates forgetting on real data.

21 / METRICS CHECKPOINT · 28 SEPTEMBER 2026

Hit@K replaces the Recall@K label, and the classical study can hold out several targets per user.

FACT Both evaluators counted whether the one hidden item reached the top K and called it Recall@K. With one target that is Hit@K, the name the original SASRec paper uses. Both workstreams now report hit@K; no score changed. This follows the discussion in issue #8.

FACT cp4285 classical sweep|stream|study --targets m holds out each user's last m events as test targets and the m before them as validation targets (data.py). Each user is scored once and every target is ranked (evaluate.py, per_user):

MetricPer user, with m targets
Hit@K1 if any target is in the top K
Recall@KTargets in the top K divided by min(m, K)
NDCG@KDCG of the targets in the top K over the ideal DCG of min(m, K) hits
MRR1 / rank of the best-ranked target

FACT With m = 1 the split, sampled users, ranks and per-user NDCG are bit-identical to the previous code (checked on synthetic data), so earlier study checkpoints still resume. sweep --split test now adds the validation event to the history, as study already did; before this it predicted two steps ahead.

INFERENCE m > 1 is a protocol change. Its scores are not comparable with m = 1 scores, and the neural pilot still has one target per user. The team should choose m for both workstreams before reporting it.

Evidence: tests (hand-computed Hit, Recall, NDCG and MRR for several targets). All 41 tests passed at this checkpoint.
